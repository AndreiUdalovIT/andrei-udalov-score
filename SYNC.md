# Синхронизация football-data

## Подготовка

Команды выполняются из корня проекта с Node.js 24 и версией pnpm из `package.json`.

В локальном `.env.local` задаются переменные из `.env.example`.

- `DATABASE_URL` — подключение приложения к выбранной ветке Neon.
- `DATABASE_URL_UNPOOLED` — прямое подключение к той же ветке для миграций и Studio.
- `FOOTBALL_DATA_TOKEN` — серверный токен football-data.org.
- `REVALIDATE_SECRET` — серверный секрет endpoint сброса кеша.

Значения в окружении процесса имеют приоритет перед `.env`-файлами.
Перед записью проверьте выбранный проект и ветку в Neon Console. Для локальной
разработки используется отдельная dev-ветка. Доступ к production настраивается отдельно.

Схема целевой БД должна содержать миграции `0000_init`,
`0001_nullable_scorer_stats`, `0002_sync_run_competitions`,
`0003_standings_context` и `0004_standings_snapshots`.
Токен и строки подключения храните в локальном окружении или секретах сервиса.

## Режимы запуска

| Режим   | Загружаемые данные                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `seed`  | Текущий сезон и до трёх предыдущих сезонов из каталога API, актуальные составы клубов            |
| `full`  | Команды, все матчи текущего сезона, общая таблица, бомбардиры и актуальные составы клубов        |
| `light` | Команды, матчи текущего сезона в окне ±7 дней от даты запуска по UTC, общая таблица и бомбардиры |

Первоначальная загрузка одного турнира с глубиной истории по умолчанию.

```powershell
pnpm sync:seed --competition PL
```

Глубину можно задать явно. Значение `0` загружает текущий сезон и актуальные составы.

```powershell
pnpm sync:seed --competition PL --history-seasons 1
```

Полное обновление текущего сезона.

```powershell
pnpm sync:full --competition PL
```

Обновление матчей рядом с текущей датой, таблицы и бомбардиров.

```powershell
pnpm sync:light --competition PL
```

Обе границы окна `light` включены. Его даты вычисляются один раз на весь запуск.
Составы клубов обновляются через `full` и `seed`.

Для нескольких турниров повторяйте `--competition`. Доступность каждого турнира
и исторического сезона зависит от доступа токена к API.

```powershell
pnpm sync:full --competition PL --competition CL
```

Справка доступна через `--help` у каждой команды. Коды завершения процесса
равны `0` при успехе или выводе справки, `2` при ошибке аргументов и `1` при
ошибке синхронизации или занятой блокировке.

Год сезона обозначает год его начала. `seed` обрабатывает выбранную историю
от старых сезонов к новым, затем обновляет текущий сезон и составы.
Ошибка обязательной операции, включая отказ API в доступе к выбранному сезону,
завершает весь запуск с ошибкой. Успешно записанные наборы данных сохраняются.

Запросы к football-data.org запускаются с интервалом минимум 6 секунд в одном
процессе для одного токена. При 429 и 5xx возможны ещё две попытки с паузой.
Итоговые строки CLI выводятся после успешного сохранения статуса запуска.
Числа в них отражают обработанные данные API, включая уже существующие записи.

Команды `sync:teams`, `sync:matches`, `sync:standings`, `sync:scorers`
и `sync:squad` предназначены для отдельных операций. Они работают без общего
журнала и блокировки. Используйте их последовательно при остановленных
`full`, `light` и `seed`. Команды и участников сезона загружайте до матчей,
таблицы и бомбардиров. Параметры каждой операции перечислены в её `--help`.

## История таблиц

`full`, `light` и завершающий этап `seed` сохраняют официальный снимок текущей
таблицы вместе с её обновлением. В `standings_snapshots` источник обозначается
как `official`, а `captured_at` содержит время получения ответа API.

Для загрузки расчётных таблиц по турам добавьте `--standings-history` к `seed`.

```powershell
pnpm sync:seed --competition PL --history-seasons 3 --standings-history
```

Флаг включает историю для PL, PD, BL1, SA и FL1. Для остальных выбранных турниров
сохраняется обычная загрузка `seed`. Завершённые сезоны загружаются по всем турам
из сезонной конфигурации, текущий — до тура из повторно запрошенного каталога API.
При текущем туре `0` диапазон пустой. Неизвестный текущий тур или отсутствие
сезонной конфигурации завершают импорт с ошибкой. Сейчас настроены сезоны 2023–2026.

Каждый тур требует отдельного запроса API. При планировании запуска учитывайте
интервал между запросами и дополнительные обращения обычного `seed`.

Для отдельного тура или диапазона сначала загрузите турнир и команды нужного
сезона, затем используйте одну из команд.

```powershell
pnpm sync:standings --competition PL --season 2025 --matchday 10
pnpm sync:standings --competition PL --season 2025 --through-matchday 38
```

Оба параметра требуют `--season` и выбираются по отдельности.
`--through-matchday` загружает туры от 1 до указанного включительно для пяти
национальных лиг с настроенным сезоном. Диапазон проверяет число команд и основной
этап таблицы. Пустой ответ истории завершает операцию с ошибкой.

Снимки по турам получают источник `reconstructed`. API рассчитывает такие таблицы
по результатам матчей и исключает снятые очки. Переносы и исправления результатов
могут изменить таблицу при повторной загрузке.
[История таблиц football-data.org](https://docs.football-data.org/general/v4/competition.html#_standings)

Успешно записанные снимки сохраняются при сбое последующего тура. Повторный запуск
добавляет наблюдения с новым временем получения. Каждая версия хранит исходные
позиции, очки и контекст таблицы.

Серверный запрос `getCompetitionStandingsHistory` принимает турнир, сезон и источник.
Для каждого тура выбирается последнее наблюдение по времени получения и ID.
`tableComplete` проверяет ожидаемое число уникальных команд и основной этап.
`coverage` перечисляет полные и пропущенные туры от 1 до последнего сохранённого
тура в пределах сезона. Для сезона без конфигурации `tableComplete` и `coverage`
возвращаются как `null`.

## GitHub Actions

Workflow `.github/workflows/sync.yml` запускает `full` и `light`.
Для первого ручного запуска файл должен находиться в `main`.
[Ручной запуск workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

В Settings → Environments создайте `development` и `production`.
В каждом окружении задайте секреты `DATABASE_URL` и `FOOTBALL_DATA_TOKEN`.
Используйте отдельные ветки Neon. Production-подключение должно соответствовать
базе сайта на Vercel, а схема каждой базы должна содержать миграции из раздела подготовки.
[Секреты окружений](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

В Settings → Secrets and variables → Actions → Variables задайте repository variables.

- `SYNC_COMPETITIONS` — коды турниров через пробел, например `PL PD BL1 SA FL1 CL ELC`.
- `SYNC_SCHEDULE_ENABLED` — `false` при подготовке и `true` после успешной ручной проверки production.

### Сброс кеша приложения

В каждом GitHub Environment задайте секрет `REVALIDATE_SECRET` и environment
variable `REVALIDATE_URL` — полный HTTPS-адрес `/api/revalidate` нужного сайта.
Для production: `https://andrei-udalov-score.vercel.app/api/revalidate`.
Deployment по этому адресу должен читать ту же ветку Neon, что и `DATABASE_URL`
выбранного GitHub Environment. Это нужно проверить отдельно и для development.

В серверном окружении соответствующего deployment на Vercel задайте такое же
значение `REVALIDATE_SECRET`. Значения для development и production должны
различаться. Сгенерировать секрет можно локально:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Если Preview защищён Vercel Authentication, в настройках проекта Vercel откройте
Settings → Deployment Protection → Protection Bypass for Automation и создайте
секрет для GitHub Actions. Сохраните его в GitHub Environment `development`
под именем `VERCEL_AUTOMATION_BYPASS_SECRET`.

Workflow передаёт этот секрет заголовком `x-vercel-protection-bypass`.
Приложение продолжает отдельно проверять `REVALIDATE_SECRET`.
Для deployment без такой защиты bypass-секрет необязателен.
[Protection Bypass for Automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)

После настройки переменных нужен новый deployment. Workflow проверяет URL,
наличие секрета, режим и известные коды турниров до начала записи в БД.

После успешной синхронизации отдельный шаг `Revalidate application cache`
отправляет POST с режимом и турнирами. Сбрасываются общие данные команд,
запросы матчей по ID и данные выбранных турниров; для `full` также составы.
Секрет передаётся в заголовке Authorization. Переходы по HTTP-редиректам
не выполняются, тело ответа не выводится. Для временных ошибок предусмотрены
до двух повторов HTTP-запроса.

Если этот шаг завершился с ошибкой, сохранённые данные остаются в БД, а запись
синхронизации может иметь статус `ok`. Ошибку сброса кеша показывает workflow.
После исправления настройки откройте Run workflow, выберите то же окружение,
режим и турниры и установите `revalidate_only=true`. Такой запуск повторяет
только сброс кеша, без обращений к football-data.org и записи в БД.
Перед этим подтвердите успешную синхронизацию выбранных данных в журнале.

Перед слиянием ветки с новой миграцией установите `SYNC_SCHEDULE_ENABLED=false`
и дождитесь завершения активных запусков. После production-deployment проверьте
применение миграций и доступность endpoint, затем верните флаг в `true`.
Это исключает запуск нового sync-кода до завершения миграции на Vercel.

### Первый запуск

1. Установите `SYNC_SCHEDULE_ENABLED=false`.
2. В Actions → Sync football data → Run workflow выберите ветку `main`,
   окружение `development`, режим `light` и турнир `PL`.
3. Дождитесь успешного завершения и проверьте новую запись `ok` в журнале dev-базы.
4. Выполните ручной `full` в окружении `production`. В поле competitions
   укажите список кодов из `SYNC_COMPETITIONS`.
5. Проверьте успешное завершение и запись `ok` с режимом `full` и выбранными
   турнирами в журнале production-базы. После этого установите
   `SYNC_SCHEDULE_ENABLED=true` и проверьте ближайший плановый запуск.

Ручной запуск использует выбранное окружение и параметры формы.
Cron использует `production` и значение `SYNC_COMPETITIONS`.
Общая очередь объединяет оба окружения и режима. Для плановой остановки
расписания установите `SYNC_SCHEDULE_ENABLED=false` и дождитесь завершения
работающих запусков.

### Расписание и наблюдение

- `light` — `17 */4 * * *` по UTC, то есть 03:17, 07:17, 11:17, 15:17,
  19:17 и 23:17 по Москве.
- `full` — `37 1 * * *` по UTC, то есть ежедневно в 04:37 по Москве.

GitHub допускает задержки и пропуски cron при высокой нагрузке. В публичном
репозитории расписание автоматически отключается после 60 дней без активности.
Для восстановления установите флаг расписания в `false`, включите workflow
в Actions, выполните ручной production-`full` и проверьте журнал. После успешного
запуска верните флаг в `true` и проверьте ближайший cron.
[Ограничения schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

Подпишитесь на репозиторий через Watch.
В личных настройках GitHub → Notifications → System → Actions включите уведомления
на GitHub или по email и выберите Only notify for failed workflows.
Уведомления cron получает создатель workflow, а после изменения cron — автор изменения.
При повторном включении workflow получатель меняется на включившего его пользователя.
[Настройка уведомлений](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications),
[получатели уведомлений](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs)

Проверяйте Actions и `sync_runs` в соответствующей ветке Neon. При отмене или
достижении таймаута workflow в 45 минут может остаться запись `running`.
Порядок её завершения описан ниже в разделе восстановления.

### Лимиты сервисов

Ограничения сверены 8 ноября 2026 года. Для football-data.org Free опубликован
лимит 10 запросов в минуту. Клиент проекта выдерживает минимум 6 секунд между
стартами запросов в одном процессе.
[Политика API](https://docs.football-data.org/general/v4/policies.html)

Для Neon Free опубликованы 100 CU-часов compute и 5 GB исходящего трафика в месяц,
1 GB Postgres-хранилища и 10 веток на проект. Расход compute учитывает все
вычислительные узлы проекта, включая dev и production. Перед включением
расписания сверьте фактический тариф и расход ресурсов в Neon Console.
[Лимиты Neon](https://neon.com/docs/introduction/plans)

## Проверка результата

В Neon SQL Editor выберите ту же ветку, на которую указывает `DATABASE_URL`,
и выполните запрос журнала.

```sql
SELECT id, mode, competition_codes, status, started_at, finished_at, requests, error
FROM public.sync_runs
ORDER BY id DESC
LIMIT 20;
```

- `running` — запуск удерживает общую блокировку.
- `ok` — все обязательные операции и сохранение итогового статуса завершились успешно.
- `error` — запуск завершился с ошибкой, часть данных могла быть записана.
- `competition_codes` — нормализованные коды выбранных турниров. У старых записей
  со значением `NULL` область обновления неизвестна.
- `requests` — число начатых HTTP-попыток к football-data.org, включая повторы.
  Счётчик записывается при завершении запуска. Значение у оборванного запуска
  может остаться нулевым после фактически выполненных запросов.

Обновление каждого набора данных выполняется отдельной короткой транзакцией.
При повторном запуске матчи обновляются по ID с проверкой `last_updated`,
а участники сезона, таблица, бомбардиры и составы сверяются с полученным набором.

## Восстановление после прерывания

Запись `running` блокирует новые `full`, `light` и `seed` во всей целевой БД,
включая другие турниры. После аварийной остановки она сохраняется до ручного
завершения. Возраст записи сам по себе недостаточен для решения о восстановлении.

1. Найдите нужный `id` в журнале и сопоставьте режим, турниры и время начала
   с прерванным запуском.
2. Подтвердите завершение владельца запуска. Для локальной команды проверьте
   завершение её Node-процесса. Для запуска в GitHub Actions проверьте окончательный
   статус соответствующего workflow. При необходимости остановите процесс
   и дождитесь завершения. На время восстановления приостановите другие запуски.
3. Повторно прочитайте запись с этим `id`. Если статус уже `ok` или `error`,
   переходите к проверке результата или повторному запуску.
4. Для подтверждённо остановленного запуска со статусом `running` выполните
   запрос ниже в выбранной ветке Neon. Замените `<RUN_ID>` на найденный числовой
   идентификатор. Условие по статусу защищает от изменения уже завершённой записи.

```sql
BEGIN;

UPDATE public.sync_runs
SET status = 'error',
    finished_at = now(),
    error = 'sync process stopped before completion'
WHERE id = <RUN_ID>
  AND status = 'running'
RETURNING id, mode, competition_codes, status, started_at, finished_at, requests, error;

COMMIT;
```

Успешное закрытие возвращает одну строку со статусом `error`. Если строк нет,
повторно проверьте журнал. Поле `requests` сохраняет прежнее значение, точное
число API-попыток аварийно остановленного процесса восстановить из него нельзя.

Повторите исходную команду с теми же турнирами и глубиной истории. Она заново
обработает выбранные данные с сохранением их идентификаторов и обновит журнал.
У `light` окно рассчитывается относительно даты повторного запуска.
После завершения проверьте код выхода и новую запись `ok` в журнале.
