# Синхронизация football-data

## Подготовка

Команды выполняются из корня проекта с Node.js 24 и версией pnpm из `package.json`.

В локальном `.env.local` задаются переменные из `.env.example`.

- `DATABASE_URL` — подключение приложения к выбранной ветке Neon.
- `DATABASE_URL_UNPOOLED` — прямое подключение к той же ветке для миграций и Studio.
- `FOOTBALL_DATA_TOKEN` — серверный токен football-data.org.

Значения в окружении процесса имеют приоритет перед `.env`-файлами.
Перед записью проверьте выбранный проект и ветку в Neon Console. Для локальной
разработки используется отдельная dev-ветка. Доступ к production настраивается отдельно.

Схема целевой БД должна содержать миграции `0000_init`,
`0001_nullable_scorer_stats` и `0002_sync_run_competitions`.
Токен и строки подключения храните в локальном окружении или секретах сервиса.

## Режимы запуска

| Режим   | Загружаемые данные                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `seed`  | Текущий сезон и до трёх предыдущих сезонов из каталога API, актуальные составы клубов            |
| `full`  | Команды, все матчи текущего сезона, общая таблица, бомбардиры и актуальные составы клубов        |
| `light` | Команды, матчи текущего сезона в окне ±7 дней от даты запуска по UTC, общая таблица и бомбардиры |

Первоначальная загрузка одного турнира с глубиной истории по умолчанию.

```powershell
pnpm sync:seed --competition PL
```

Глубину можно задать явно. Значение `0` загружает текущий сезон и актуальные составы.

```powershell
pnpm sync:seed --competition PL --history-seasons 1
```

Полное обновление текущего сезона.

```powershell
pnpm sync:full --competition PL
```

Обновление матчей рядом с текущей датой, таблицы и бомбардиров.

```powershell
pnpm sync:light --competition PL
```

Обе границы окна `light` включены. Его даты вычисляются один раз на весь запуск.
Составы клубов обновляются через `full` и `seed`.

Для нескольких турниров повторяйте `--competition`. Доступность каждого турнира
и исторического сезона зависит от доступа токена к API.

```powershell
pnpm sync:full --competition PL --competition CL
```

Справка доступна через `--help` у каждой команды. Коды завершения процесса
равны `0` при успехе или выводе справки, `2` при ошибке аргументов и `1` при
ошибке синхронизации или занятой блокировке.

Год сезона обозначает год его начала. `seed` обрабатывает выбранную историю
от старых сезонов к новым, затем обновляет текущий сезон и составы.
Ошибка обязательной операции, включая отказ API в доступе к выбранному сезону,
завершает весь запуск с ошибкой. Успешно записанные наборы данных сохраняются.

Запросы к football-data.org запускаются с интервалом минимум 6 секунд в одном
процессе для одного токена. При 429 и 5xx возможны ещё две попытки с паузой.
Итоговые строки CLI выводятся после успешного сохранения статуса запуска.
Числа в них отражают обработанные данные API, включая уже существующие записи.

Команды `sync:teams`, `sync:matches`, `sync:standings`, `sync:scorers`
и `sync:squad` предназначены для отдельных операций. Они работают без общего
журнала и блокировки. Используйте их последовательно при остановленных
`full`, `light` и `seed`. Команды и участников сезона загружайте до матчей,
таблицы и бомбардиров. Параметры каждой операции перечислены в её `--help`.

## Проверка результата

В Neon SQL Editor выберите ту же ветку, на которую указывает `DATABASE_URL`,
и выполните запрос журнала.

```sql
SELECT id, mode, competition_codes, status, started_at, finished_at, requests, error
FROM public.sync_runs
ORDER BY id DESC
LIMIT 20;
```

- `running` — запуск удерживает общую блокировку.
- `ok` — все обязательные операции и сохранение итогового статуса завершились успешно.
- `error` — запуск завершился с ошибкой, часть данных могла быть записана.
- `competition_codes` — нормализованные коды выбранных турниров. У старых записей
  со значением `NULL` область обновления неизвестна.
- `requests` — число начатых HTTP-попыток к football-data.org, включая повторы.
  Счётчик записывается при завершении запуска. Значение у оборванного запуска
  может остаться нулевым после фактически выполненных запросов.

Обновление каждого набора данных выполняется отдельной короткой транзакцией.
При повторном запуске матчи обновляются по ID с проверкой `last_updated`,
а участники сезона, таблица, бомбардиры и составы сверяются с полученным набором.

## Восстановление после прерывания

Запись `running` блокирует новые `full`, `light` и `seed` во всей целевой БД,
включая другие турниры. После аварийной остановки она сохраняется до ручного
завершения. Возраст записи сам по себе недостаточен для решения о восстановлении.

1. Найдите нужный `id` в журнале и сопоставьте режим, турниры и время начала
   с прерванным запуском.
2. Подтвердите завершение владельца запуска. Для локальной команды проверьте
   завершение её Node-процесса. Для запуска в GitHub Actions проверьте окончательный
   статус соответствующего workflow. При необходимости остановите процесс
   и дождитесь завершения. На время восстановления приостановите другие запуски.
3. Повторно прочитайте запись с этим `id`. Если статус уже `ok` или `error`,
   переходите к проверке результата или повторному запуску.
4. Для подтверждённо остановленного запуска со статусом `running` выполните
   запрос ниже в выбранной ветке Neon. Замените `<RUN_ID>` на найденный числовой
   идентификатор. Условие по статусу защищает от изменения уже завершённой записи.

```sql
BEGIN;

UPDATE public.sync_runs
SET status = 'error',
    finished_at = now(),
    error = 'sync process stopped before completion'
WHERE id = <RUN_ID>
  AND status = 'running'
RETURNING id, mode, competition_codes, status, started_at, finished_at, requests, error;

COMMIT;
```

Успешное закрытие возвращает одну строку со статусом `error`. Если строк нет,
повторно проверьте журнал. Поле `requests` сохраняет прежнее значение, точное
число API-попыток аварийно остановленного процесса восстановить из него нельзя.

Повторите исходную команду с теми же турнирами и глубиной истории. Она заново
обработает выбранные данные с сохранением их идентификаторов и обновит журнал.
У `light` окно рассчитывается относительно даты повторного запуска.
После завершения проверьте код выхода и новую запись `ok` в журнале.
